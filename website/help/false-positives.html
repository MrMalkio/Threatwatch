When Threatwatch blocks something you wanted

Treat a broken page as a debugging problem, not proof that the blocked destination was harmless.

Getting startedWatch modesDownloadsFalse positivesFAQ

1. Read the catch

Open the Threatwatch popup or watchlist and identify the event type, action, target, and protection layer. A popup block is different from a download cancellation, protocol launch, or external navigation block.

2. Ask what the site was trying to do

  • Was it navigating away from the protected hostname?
  • Was a new tab created?
  • Was the destination a player host, an ad network, an unknown redirect, or a custom protocol?
  • Did the response try to become a download?
  • Did a fake verification flow appear at the same time?

3. Verify independently

Search the destination through a trusted reputation source or inspect the request in a disposable test profile. Do not approve a host solely because other users say it is required.

4. Make the smallest possible change

Current profiles support allowed top-level destination domains. Add an exact destination only when you have a reason to trust that navigation. Avoid broad parent-domain exceptions.

Never approve a command-paste prompt, executable download, or unknown custom protocol just to make playback work.

5. Undo the change if behavior gets worse

Remove the allowlisted destination and return the site to Strict or Learn. Threatwatch's community roadmap includes one-use exceptions, expiring overrides, and a formal false-positive report flow.

Report a bug

If Threatwatch itself behaves incorrectly, open a GitHub issue. Do not post secrets, cookies, account credentials, or live malware samples.
