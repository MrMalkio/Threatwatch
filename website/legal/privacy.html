Privacy policy

Threatwatch 0.4.0 is local-first. The current extension has no Threatwatch telemetry backend, no user account system, and no advertising network.

1. Scope

This policy describes how the Threatwatch Project and its maintainers, referred to here as “Threatwatch,” “we,” or “us,” handle information through the Threatwatch Chrome extension and this public website. It does not govern third-party websites you visit through your browser.

2. Current extension data practices

Threatwatch processes browser information locally so it can provide the protections the user requests. Current local data can include:

  • Protected domain names, display labels, watch modes, enabled or paused state, destination allowlists, and global blocklist entries.
  • Threat events such as event type, action, timestamp, profile identifier, source layer, and sanitized source or target URL.
  • Runtime health information used to determine whether protection rules synchronized successfully.
  • Watchlist view preferences such as sorting, filtering, search view state, and expanded profile rows.
  • Temporary tab and navigation context used to attribute redirects, spawned tabs, and downloads to a protected site.

Threatwatch uses Chrome APIs to read or react to tabs, navigation, downloads, page behavior, and other browser events needed for its protection features. This processing happens inside the user's browser in the current release.

3. What Threatwatch 0.4.0 does not send to us

  • No full browsing history is uploaded to Threatwatch.
  • No account identifier, email address, password, cookie, authentication token, payment data, or advertising identifier is sent to a Threatwatch backend because no Threatwatch backend exists in the current release.
  • No media title, search term, page title, screenshot, form content, or page text is uploaded to Threatwatch.
  • Threatwatch does not sell or share browsing data for advertising, profiling, data brokerage, or cross-context behavioral advertising.

4. URL sanitization

Local threat-event storage removes credentials, query strings, fragments, control characters, and non-web payload content before persistence. HTTP and HTTPS event records keep the origin and path needed to understand the catch. Malformed inputs are replaced with a fixed invalid marker rather than stored raw.

5. Local retention and controls

Profile settings and threat events remain in browser storage until the user changes or clears them, resets the extension, or removes the extension and Chrome removes its associated extension storage. Temporary session navigation context is intended to expire with the browser session. Users can clear threat events and remove site profiles from the extension interface.

6. Public website

This website is static. Threatwatch does not currently place first-party analytics cookies, advertising cookies, tracking pixels, or analytics scripts on the site. The site is intended to be hosted through GitHub Pages. GitHub and network providers may process ordinary request metadata such as IP address, user agent, requested path, and timestamps under their own terms and privacy practices. Threatwatch does not control GitHub's infrastructure logs.

7. GitHub interactions

If you open an issue, pull request, discussion, security report, or other interaction on GitHub, GitHub processes that information under its own policies. Do not place secrets, private account information, cookies, credentials, or sensitive personal information in public repository issues.

8. Future community features

Community-sourced domain reputation, feedback submission, anonymous aggregate threat telemetry, accounts, cloud sync, and paid services are roadmap items, not current 0.4.0 behavior. Before any feature begins transmitting browsing-related or personal data to Threatwatch, the product must provide a clear in-product disclosure, obtain consent when required, update this policy, and limit collection to what the user-facing feature needs.

The proposed community design calls for hostname-level and coarse evidence data rather than full URLs, media titles, search terms, or chronological browsing logs.

9. Chrome Web Store Limited Use

Threatwatch's use of information received from Chrome APIs will comply with the Chrome Web Store User Data Policy, including its Limited Use requirements. Browsing activity will be used only to provide or improve the user-facing Threatwatch security features for which it is needed. Threatwatch will not sell that data or use it for personalized advertising.

Chrome's current policies require accurate privacy disclosures, limit collection of browsing activity to disclosed user-facing features, and require secure handling when user data is transmitted. See the Chrome Web Store Program Policies.

10. Security

No software can promise absolute security. Threatwatch uses local storage separation, URL sanitization, signed-code distribution through the repository, Manifest V3 restrictions, and fail-closed protection synchronization. If server-backed features are added, transmitted personal data must use modern transport encryption and appropriate access controls.

11. Children

Threatwatch is intended for adults. The public service is not directed to children under 13, and planned community account features should not be offered to minors until age, consent, and applicable-law requirements are reviewed.

12. Privacy rights

Privacy laws in some jurisdictions may provide rights to access, correct, delete, or obtain information about personal data a covered business maintains. The current Threatwatch release does not maintain a Threatwatch server-side user database. If that changes, this policy will identify the applicable request process. Rights that cannot legally be waived remain available where the law applies.

13. Changes to this policy

We may update this policy when the product changes, the law changes, or a new data practice is proposed. A change that materially expands data collection will be disclosed before the new collection begins when required by law or platform policy.

14. Contact

Use the Threatwatch GitHub issue tracker for non-sensitive privacy questions. Do not post private data in a public issue. For a sensitive security matter, use the repository's Security area and private reporting path when available.
